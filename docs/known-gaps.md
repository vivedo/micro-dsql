# Known gaps

Deviations from Aurora DSQL / PostgreSQL that micro-dsql knowingly has, per constitution
Principle V. Each entry: what is observed, the suspected cause, and the milestone expected to
close it. Blocker ids (B1–B14) refer to the M0 spike findings (research/06 §9).

**Skipped tests:** none for known gaps. The only `#[ignore]`d Rust test is the manual timing
check `autocommit_latency` in `tests/occ/autocommit.rs`, and `tests/psql/known-gaps.txt` is
empty: all five T1 layer-1 scenarios pass against micro-dsql. The entries below are gaps without a
failing test in the suite (probes and M0 findings), kept here so they are not forgotten.

Fixed in M1 (with tests in `crates/server/tests/smoke/`): B4 (Terminate closes the connection), B5 (foreign
keys enforced, `23503`, `ON DELETE CASCADE`), B9 except the items below, and most of B1–B3.

Fixed in M2 (tests in `crates/server/tests/smoke/dsql_*.rs` and `crates/policy`): B13 (the DSQL
deny rules, transaction discipline and limits), the SET whitelist part of B9, the
`SET SESSION CHARACTERISTICS` entry, the `55P03` mapping of B10, DSQL's OC000/OC001 error shapes,
and the bare-`numeric` rewrite of B6.

Fixed in M3 (tests in `crates/server/tests/smoke/dsql_ddl.rs`, `dsql_jobs.rs`, `crates/policy`): the
`CREATE INDEX ASYNC` / `sys.*` / identity / `CACHE` / `ALTER TABLE` parts of B12 (details in the
new rows below), and DSQL's rules for `CREATE INDEX`, identity columns, sequences and `ALTER TABLE`.

Fixed in M4 (tests in `tests/occ/`, `crates/server/tests/smoke/dsql_locking.rs`, `crates/policy`):
B10 (autocommit statements run as single-statement transactions, so `55P03` never reaches a
client; residual contention is retried for a bounded time, then `40001` OC001), the autocommit
row limit and the atomicity of multi-statement strings, conflicts reported at `COMMIT`, the
snapshot taken at `BEGIN`, and `SELECT ... FOR UPDATE`. The differences that remain are the
`OCC:` rows below; B11 is refined.

| Id | Observed | Suspected cause | Milestone |
|---|---|---|---|
| B1 (rest) | Describe reports the right parameter count, and types from casts (`$1::int8`), column context (`col = $1`, `INSERT … VALUES`, `UPDATE … SET col = $1`) and `LIMIT/OFFSET`. Parameters in other positions (function arguments, arithmetic, `= ANY($1)`, subqueries) are described as `text`; asyncpg then refuses non-string arguments client-side. | The engine does not infer parameter types; micro-dsql infers them from the AST with simple rules (`crates/policy/src/params.rs`). | M2 (more rules) / upstream (translator type inference) |
| B2 (rest) | Binary parameters for `interval`, `time`, arrays and other types not in the supported list fail with `22P03`. `numeric` parameters are bound as floating point. | Decoders exist only for common OIDs (`crates/server/src/binary.rs`); the engine has no exact decimal (B6). | M2 |
| B3 (rest) | `sum()`, `avg()`, `min()/max()` over expressions and other untyped expressions are described as `text`; `real` columns are reported as `float8`. | The engine reports no type for these expressions; micro-dsql only overrides `count()` (→ `int8`) and boolean expressions (→ `bool`). | M2 / upstream |
| B6 | `numeric(p,s)` arithmetic and aggregates are computed in floating point (`sum` = `53.230000000000004`). Bare `numeric` columns are now declared `numeric(18,6)` as on DSQL. | Engine has no decimal type (stores REAL). | upstream |
| B7 | `timestamptz` literals with `+00`/`+01` offsets fail with `22007 invalid timestamp value`; microseconds are truncated to milliseconds; no `date_trunc`, no interval arithmetic (`interval '1 day' + interval '2 hours'` returns `3`). | Engine date/time support. | upstream |
| B8 | jsonb `@>` returns no rows instead of matching; `?`, `#>>`, `jsonb_build_object` missing. | Engine JSON support. | upstream |
| B9 (rest) | `current_user`/`session_user` are `postgres` (DSQL: the login role, e.g. `admin`). With `--data <file>`, `current_database()` is the file's stem (only the default in-memory database is `postgres`). `SET timezone` accepts only UTC spellings (`22023` otherwise). | Engine roles and naming; the engine has only UTC. | later |
| B11 | Any committed DDL fails every concurrent writing transaction with `40001` OC001 at its `COMMIT`, whether or not it touched the table (DSQL: only conflicting transactions). While another session's DDL transaction is open, an unrelated write (autocommit or in a transaction) fails with `40001` OC000 at its `COMMIT`, and DDL statements wait for it (autocommit DDL is retried for up to about 200 ms, then OC001); under steady DDL churn unrelated writers therefore see OC000 (research E-P9). Clients that retry `40001`, as DSQL's do, are unaffected. Test: `differences::d5_unrelated_ddl_conflicts_with_writers`. | Schema cookie is database-wide and a DDL transaction is exclusive in the engine. | upstream |
| B12 (rest) | `information_schema` missing; `DELETE ... USING`, `ALTER COLUMN SET/DROP DEFAULT`, `ALTER COLUMN DROP NOT NULL`, `ALTER TABLE DROP CONSTRAINT`, `ADD COLUMN IF NOT EXISTS`, identity `ALTER COLUMN` forms (`ADD GENERATED`, `SET GENERATED`), `ADD UNIQUE USING INDEX` (DSQL answers `55000` while the index builds; micro-dsql builds synchronously) and `SET STORAGE` are rejected by the engine (`0A000`/`42601` with the engine's text). | Engine / DSQL-specific syntax. | later |
| M3: NOT VALID rebuild | `ADD CONSTRAINT ... FOREIGN KEY / CHECK ... NOT VALID` is done by rebuilding the table (new table with the constraint, rows copied unchecked, old table dropped, new one renamed, indexes recreated) because the engine can neither add a foreign key to an existing table nor add a CHECK without validating the rows. Differences from DSQL: the copy takes time proportional to the table (DSQL: constant); the table and its indexes get new oids (the `sys.jobs` rows that name them are updated); a concurrent writing transaction fails with `40001` (OC001) as after any DDL, and lock contention while the rebuild transaction starts is retried for up to about 200 ms before it too is OC001; the foreign key must reference a table of the same schema (`0A000` otherwise); `pg_constraint.convalidated` stays `true` (see the next row); only single-column foreign keys and single-column CHECKs are accepted (other forms: `0A000 unsupported NOT VALID constraint form: ...`). The rebuild opens its own transaction when the session is idle (`constraints::in_internal_transaction`, which runs through `occ::internal_transaction`). Evidence: specs/006-m3-orm-ddl/research.md sections 6 and 8. | Engine has no ADD CONSTRAINT. | later (engine support) |
| M3: constraint state | `pg_constraint.convalidated` is `true` for every constraint, including a CHECK added `NOT VALID` before its `VALIDATE`; `ALTER TABLE ASYNC ... VALIDATE CONSTRAINT` on an already valid constraint completes. | The engine's catalog has no not-validated state. | later |
| M3: jobs | Jobs are synchronous: `CREATE INDEX ASYNC` and `VALIDATE` finish before the statement returns, so `sys.jobs` only has `completed` and `failed` rows (no `submitted`/`processing`) and no `DROP` jobs. A failed unique build leaves no invalid index; inside an explicit transaction the engine aborts the transaction instead (`23505`, then `25P02`). | micro-dsql has no background work. | later |
| M3: `sys` | `sys` and `sys.jobs` are an ordinary schema and table: they show in `pg_namespace` / `pg_tables`, and the `oid` columns (`class_id`, `object_id`) are described as `integer`. The `VALIDATE_CONSTRAINT` job type, the `22023 job <id> not found` text for an unknown well-formed id and `SELECT sys.dsql_major_version()` forms beyond the two documented are not verified against a live cluster. | The engine has no views over its own catalog or `oid` type in result descriptions. | when verified on a live cluster |
| M3: identity and sequences | `GENERATED ALWAYS` behaves like `BY DEFAULT` (an explicit value is stored instead of `428C9`). `pg_sequences.cache_size` is `1` whatever `CACHE` said, and `ALTER SEQUENCE ... CACHE n` is a no-op. `DROP TABLE` drops the sequence of a column whose default is `nextval('<schema>.<table>_<column>_seq')`; an identity with a `sequence name` of its own keeps its sequence. A `CREATE TABLE` of an identity table that already exists fails on the sequence (`relation "<table>_<column>_seq" already exists`) instead of the table. | Desugared to a sequence plus a default (no ownership in the engine). | later |
| M3: index forms | `INCLUDE (...)` columns are dropped from the index and `NULLS NOT DISTINCT` is ignored (NULLs stay distinct), because the engine has neither; the statements succeed. `CREATE INDEX async ON t (c)` is read as `CREATE INDEX ASYNC ON t (c)` (an unnamed async index), as on DSQL; `"async"` (quoted) is an index name. | Engine index syntax. | later |
| M3: command tags | `RETURNING` results and `SHOW` answer with the number of rows appended to the tag (`SELECT 1` instead of `INSERT 0 1`); only the job statements carry a tag without a count (`CREATE INDEX`, `ALTER TABLE`, `CALL`). | pgwire appends the row count to every result set. | later |
| M3: ADD COLUMN | `ADD COLUMN IF NOT EXISTS` is refused by the engine (`0A000 ALTER TABLE ADD COLUMN IF [NOT] EXISTS is not supported`) although DSQL accepts a plain one. | Engine. | later |
| OCC: later writer loses | DSQL fails the later *committer*; micro-dsql fails the later *writer*: a write that meets another transaction's uncommitted or newer write is deferred and its transaction can no longer commit (`COMMIT` answers OC000), even when it commits first. Test: `differences::d3_the_earlier_writer_wins_even_when_the_later_one_commits_first`. | The engine detects write-write conflicts at the write; the conflict is deferred by rolling back and replaying the statement (`occ::defer_conflict`). | upstream (multi-version write sets) |
| OCC: rolled-back writer dooms | If the transaction that was written first rolls back, the second one is still doomed (DSQL: it commits). Test: `differences::d4_a_rolled_back_first_writer_still_dooms_the_second`. | Same mechanism: the conflict is decided when the second write happens. | upstream |
| OCC: doomed transaction restarts | When a conflict is deferred the engine transaction is rolled back and re-opened: the writes the transaction made before it are discarded, later statements read a fresh snapshot, and a statement that conflicts again reports no rows (`UPDATE 0`, empty `RETURNING`). `COMMIT` fails with OC000 either way, so nothing of the transaction is ever committed. Test: `differences::d4b_a_doomed_transaction_reads_a_fresh_snapshot`. | Same mechanism. | upstream |
| OCC: FOR KEY SHARE | `FOR KEY SHARE` is accepted and runs as a plain read: it never conflicts, where DSQL's conflicts with a concurrent `DELETE` or key `UPDATE` of the row. Test: `differences::d1_for_key_share_does_not_conflict_with_a_delete`. | A read-lock set validated at commit is missing from the engine's MVCC (a Turso patch, research/04). | upstream |
| OCC: foreign keys take no key share | Deleting a parent row while a child referencing it is inserted in a concurrent transaction: both commit and an orphan child remains (DSQL's implicit key share makes one fail). Test: `differences::d2_parent_delete_and_child_insert_both_commit_leaving_an_orphan`. | Same missing read-lock set. | upstream |
| OCC: FOR UPDATE forms | `SELECT ... FOR UPDATE` works on a single table (optionally `OF` that table or its alias, with `ORDER BY`/`LIMIT`/`OFFSET`); `LIMIT` is ignored by the write-set touch, so every row matching `WHERE` is locked (more conflicts than DSQL). Joins, subqueries, CTEs, set operations, `GROUP BY`/`DISTINCT` and several `OF` tables are refused with `0A000 locking clause is only supported on a single-table SELECT` (DSQL supports multi-table `FOR UPDATE`; the text is micro-dsql's own, no live record exists). Tests: `crates/policy/src/locking.rs`, `tests/occ/locking.rs`. | `FOR UPDATE` is emulated by an `UPDATE t SET c = c WHERE ...` before the read. | later |
| OCC: NOWAIT / SKIP LOCKED | `NOWAIT` and `SKIP LOCKED` are accepted and ignored (the locker never waits or skips; the conflict shows at its `COMMIT`). The research notes mark them unsupported in DSQL ([inferred]); the reference emulator accepts them. Test: `differences::nowait_and_skip_locked_are_no_ops`. | There are no row locks. | when verified on a live cluster |
| OCC: tables created after BEGIN | The snapshot is fixed at `BEGIN`, so a table another session creates afterwards does not exist for the open transaction (`42P01`; the catalog is part of the snapshot). Test: `differences::tables_created_after_begin_are_invisible`. | Snapshot isolation covers the catalog. | upstream |
| OCC: contention in a transaction | Lock contention that meets a statement inside an explicit transaction (DDL while another session holds a DDL transaction) cannot be retried and is reported as `40001` OC001, aborting the block. Outside a transaction the statement is retried. Test: `differences::residual_contention_inside_an_explicit_transaction_is_oc001`. | Retrying part of a transaction is not safe. | upstream |
| B14 | `int2` overflow gives `P0001` (PG: `22003`); `int4` overflow is not detected (`2147483647::int4 + 1` = `2147483648`). | Engine type checks. | upstream / M2 error remap |
| DEALLOCATE | `DEALLOCATE <name>` and `DEALLOCATE ALL` are answered with their command tags but do not remove protocol-level prepared statements; an unknown name is not reported (`26000` in PostgreSQL). Enough for psycopg, which sends `DEALLOCATE ALL` after DDL. | The simple-query handler cannot reach pgwire's statement store; the engine has no SQL `PREPARE`. | M2 |
| COPY | `COPY … TO STDOUT` collects all rows before sending them (upstream streamed them). | Statements now run on the blocking pool and results are materialised there. | later, if large exports matter |
| Errors | The engine's schema name leaks into some messages (`42P01 relation "main.users" does not exist` for an index on a missing table). Besides DSQL's own errors (OC000, OC001, the rule refusals) only a few engine errors are reshaped like PostgreSQL's (`42P01` message and position, `42601` position, schema name on constraint errors, `3B001` text). Other engine messages are passed through unchanged. | Error shaping covers what the scenarios and probes check (`crates/policy/src/errors.rs`). | as found |
| Row counts | The row total of a transaction is the engine's per-statement change count; rows deleted or updated by foreign-key `ON DELETE`/`ON UPDATE` actions are not counted. | The engine reports only the statement's own rows. | later |
| Rule texts without a live record | `COPY is not supported`, `LOCK TABLE is not supported`, `advisory locks are not supported`, `DO`, `CREATE PROCEDURE`, `CREATE RULE`, `CREATE PUBLICATION`, `REINDEX`, `CLUSTER`, `prepared transactions` and the `role` rules come from MiniStack or from micro-dsql itself; no live DSQL record exists. `SET SESSION CHARACTERISTICS … REPEATABLE READ` is accepted as a no-op on the strength of the `BEGIN` form. | No live cluster was available. | when verified on a live cluster |
| SET scope | Remembered settings (`datestyle`, `enable_*`, …) set with plain `SET` inside a transaction that is rolled back keep their new value (PostgreSQL reverts them). `set_config()` of a whitelisted name reaches the engine, not the remembered values; `set_config()` with a non-constant name is not checked. | Remembered values live in the policy layer, outside the engine's transactions. | later |
| Engine gaps found by the probes | The engine rejects or lacks: `CREATE FUNCTION` (`42601`, even `LANGUAGE sql`), `ANALYZE`, `DECLARE CURSOR`, `DROP TABLE a, b` (several objects), `DROP FUNCTION`, `DROP EXTENSION`, `DROP PUBLICATION`, `to_regclass()`, `CREATE TEMP VIEW` (refused with another text), and `pg_attribute` rows for user tables (so `format_type` queries return nothing). | Engine / translator coverage. | upstream / later |
