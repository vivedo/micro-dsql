## 2. Drizzle (the M3 target ORM) against micro-dsql

Throwaway project outside the repository: `drizzle-orm@0.45.4`, `drizzle-kit@0.31.11`,
`pg@8.23.1`, Node 22. Schema: `users` (bigint identity `cache: 65536`, varchar, text, boolean
default, timestamptz default now, unique index), `posts` (uuid default `gen_random_uuid()`, bigint
FK to users, text, numeric(10,2), jsonb, index), `counters` (integer identity).

**What `drizzle-kit generate` emits** (verbatim shape):

```sql
CREATE TABLE "counters" (
	"id" integer PRIMARY KEY GENERATED ALWAYS AS IDENTITY (sequence name "counters_id_seq" INCREMENT BY 1 MINVALUE 1 MAXVALUE 2147483647 START WITH 1 CACHE 1),
	"n" integer DEFAULT 0 NOT NULL
);
--> statement-breakpoint
CREATE TABLE "posts" ("id" uuid PRIMARY KEY DEFAULT gen_random_uuid() NOT NULL, "author_id" bigint NOT NULL, "title" text NOT NULL, "price" numeric(10, 2), "meta" jsonb);
--> statement-breakpoint
CREATE TABLE "users" ("id" bigint PRIMARY KEY GENERATED BY DEFAULT AS IDENTITY (sequence name "users_id_seq" INCREMENT BY 1 MINVALUE 1 MAXVALUE 9223372036854775807 START WITH 1 CACHE 65536), "email" varchar(255) NOT NULL, "name" text, "active" boolean DEFAULT true NOT NULL, "created_at" timestamp with time zone DEFAULT now() NOT NULL);
--> statement-breakpoint
ALTER TABLE "posts" ADD CONSTRAINT "posts_author_id_users_id_fk" FOREIGN KEY ("author_id") REFERENCES "public"."users"("id") ON DELETE no action ON UPDATE no action;--> statement-breakpoint
CREATE INDEX "posts_author_idx" ON "posts" USING btree ("author_id");--> statement-breakpoint
CREATE UNIQUE INDEX "users_email_idx" ON "users" USING btree ("email");
```

Observations: identities always carry `sequence name`, `INCREMENT BY`, `MINVALUE`, `MAXVALUE`,
`START WITH` and an explicit `CACHE` (default `CACHE 1`); foreign keys always come as separate
`ALTER TABLE … ADD CONSTRAINT` after all CREATE TABLEs; indexes are plain `CREATE [UNIQUE] INDEX …
USING btree`; tables come in alphabetical order.

**Stock migrator** (`drizzle-orm/node-postgres/migrator`, which `drizzle-kit migrate` also uses):

```
SQL> CREATE SCHEMA IF NOT EXISTS "drizzle"
SQL> CREATE TABLE IF NOT EXISTS "drizzle"."__drizzle_migrations" ( id SERIAL PRIMARY KEY, hash text NOT NULL, created_at bigint )
MIGRATE FAILED: 42704 type "serial" does not exist
```

`drizzle-kit migrate` exits `1` and prints no error (its spinner hides it). After the journal table,
the migrator would run **every pending migration and its journal INSERT in one transaction**
(`session.transaction(...)`), which DSQL refuses at the second DDL (`0A000 multiple ddl statements
not supported in a transaction`) and at the first INSERT (`ddl and dml are not supported in the
same transaction`). The stock migrator therefore cannot run on live DSQL either.

**Generated SQL applied statement by statement (autocommit)**, stock form:

```
ERR  0A000 WITH (storage parameters) / USING INDEX TABLESPACE on a constraint is not supported | CREATE TABLE "counters" …
OK   CREATE  | CREATE TABLE "posts" …
ERR  0A000 WITH (storage parameters) / USING INDEX TABLESPACE on a constraint is not supported | CREATE TABLE "users" …
ERR  42601 ALTER TABLE ADD CONSTRAINT is not supported | ALTER TABLE "posts" ADD CONSTRAINT …
OK   CREATE  | CREATE INDEX "posts_author_idx" ON "posts" USING btree ("author_id");
ERR  42P01 relation "main.users" does not exist | CREATE UNIQUE INDEX "users_email_idx" …
```

On live DSQL the stock form fails too: `integer` identity (`0A000 datatype integer not supported,
identity column type must be bigint`), FK without `NOT VALID` (`0A000 unsupported ALTER TABLE ADD
CONSTRAINT statement`), sync `CREATE INDEX` (`0A000 unsupported mode …`).

**DSQL-adapted form** (bigint identities; `… NOT VALID` + `ALTER TABLE ASYNC … VALIDATE CONSTRAINT
…`; `CREATE [UNIQUE] INDEX ASYNC` without `USING btree`), applied statement by statement:

```
ERR  0A000 WITH (storage parameters) / USING INDEX TABLESPACE on a constraint is not supported | CREATE TABLE "counters" …
OK   CREATE  | CREATE TABLE "posts" …
ERR  0A000 WITH (storage parameters) / USING INDEX TABLESPACE on a constraint is not supported | CREATE TABLE "users" …
ERR  42601 ALTER TABLE ADD CONSTRAINT is not supported | ALTER TABLE "posts" ADD CONSTRAINT … NOT VALID
ERR  42601 syntax error at or near ""posts"" | ALTER TABLE ASYNC "posts" VALIDATE CONSTRAINT …
ERR  42601 syntax error at or near ""posts_author_idx"" | CREATE INDEX ASYNC "posts_author_idx" …
ERR  42601 syntax error at or near ""users_email_idx"" | CREATE UNIQUE INDEX ASYNC "users_email_idx" …
```

Every M3 item is on Drizzle's path: identity (items 2–3), FK `NOT VALID` + `VALIDATE` (item 4),
`ASYNC` index (item 1). Side finding: the `42P01` text names `main.users` (the engine's internal
schema name leaks into the message); recorded under "Errors" in docs/known-gaps.md by this feature.

## 5. Decisions

**D1 — ASYNC handling: blank, don't delete.** `rewrite::pre_parse` replaces the five bytes of the
`ASYNC` keyword that directly follows `CREATE [UNIQUE] INDEX` or `ALTER TABLE` (found with
`pg_query::scan`, so comments, strings and quoted identifiers are never touched, and `CREATE INDEX
async ON t` — `async` used as the index name, followed by `ON` — is left alone) with five spaces,
and returns which kind of ASYNC it removed. Same length means every byte offset (error positions,
AST locations, later `TextEdit`s) is valid for both texts with no mapping table. The simple-query
path runs the pre-parse over the whole query string before its syntax check and splits the
**original** string (the scanner split accepts `ASYNC`); `StatementPlan::new` runs it again per
statement and records `async_kind`. The extended path does the same at Parse. Alternative: delete
the keyword and keep an offset map — rejected (every position consumer would need it).
Alternative: a Turso grammar patch — rejected (libpg_query is vendored C; not a minimal patch).

**D2 — `sys.*` in our layer, no Turso patch.** At database open the server creates `sys` and
`sys.jobs` (`CREATE SCHEMA IF NOT EXISTS`, `CREATE TABLE IF NOT EXISTS`, nine columns; `oid`
columns declared `oid`). Jobs are rows written by the server on the session's own connection, in
the session's transaction (so ROLLBACK removes them and other sessions see them after COMMIT).
`CALL sys.wait_for_job(…)`, `SELECT sys.dsql_major_version()` and `SELECT * FROM
sys.dsql_major_version()` are recognised by the policy on the AST; the policy validates the
argument (22P02, 0A000) and the server answers from `sys.jobs`. `SELECT … sys.wait_for_job(…)`
anywhere is refused (42809). Writes and DDL on `sys.*` from clients are refused (42501) by a rule.
Rationale: Principle II requires an attempt in our crates first, and it works. Alternative: a
patch registering native `sys` functions in `PostgresDialect` (research/02 §5) — not needed;
it would also be the first patch and must solve the patch-crate git constraint first.
Known differences: `oid` columns are described as `integer`; `sys` and `sys.jobs` appear in
`pg_namespace`/`pg_tables` (on DSQL `sys.jobs` is a view); only the two documented
`dsql_major_version` forms are recognised.

**D3 — Rewrite seam extensions.** `TextEdit { at, remove, insert }` (`remove = 0` keeps today's
inserts). `StatementPlan` gains `prelude: Vec<String>` (engine statements run before
`engine_sql`, same transaction), `cleanup_on_failure: Vec<String>` (run when `engine_sql` fails
outside a transaction, e.g. `DROP SEQUENCE IF EXISTS` after a failed identity CREATE TABLE),
`async_kind`, `job: Option<JobAction>` and `ddl: Option<DdlAction>` (data-model.md). The policy
still counts the client statement once for the discipline rules. Alternative: let the engine
run a multi-statement string — rejected: the engine's own simple-query handling is bypassed and
error attribution would be lost.

**D4 — CACHE.** Rules first (missing CACHE, 2..65535, non-bigint identity), then a rewrite that
replaces the CACHE value with `1` in `CREATE SEQUENCE`, `ALTER SEQUENCE` and identity options. The
value DSQL stores (`pg_sequences.cache_size`) is therefore `1` on micro-dsql (known gap).

**D5 — Identity desugaring.** For each `bigint` identity column in `CREATE TABLE`: prelude
`CREATE SEQUENCE <seq> [INCREMENT BY …] [MINVALUE …] [MAXVALUE …] [START WITH …] [CYCLE] CACHE 1`
(sequence named by the `sequence name` option or `<table>_<column>_seq`, schema of the table),
and a `TextEdit` replacing the identity constraint's text span with `DEFAULT
nextval('<schema>.<seq>')`. `GENERATED ALWAYS` behaves like `BY DEFAULT` (known gap). On `DROP
TABLE t` the server first reads `pg_attrdef` for `t`'s `nextval('<schema>.<t>_<col>_seq')`
defaults and drops those sequences after the table (as PostgreSQL does for owned sequences).
Rationale: no ownership catalog needed; Drizzle and PostgreSQL both name identity sequences
`<table>_<column>_seq`. Identity in `ALTER TABLE … ADD COLUMN` is refused by FR-031 anyway;
`ALTER COLUMN … ADD GENERATED` stays out of scope.

**D6 — Job ids and rows.** Ids are 128 random bits (`uuid` v4, already a server dependency)
encoded as 26 lower-case base-32 characters (`a-z2-7`, RFC 4648 alphabet) by a pure policy
function. The server answers `job_id` statements with the engine's command tag (`CREATE INDEX` /
`ALTER TABLE`) plus one row, through a new `Reply::Rows` / `Outcome::Rows` built from
`policy::session::ReplyColumn` types (`text`, `bool`, `int4`). Job row: `class_id 1259`,
`object_id` from `pg_class` (index or table oid), `object_name` `<schema>.<name>`, `start_time` and
`update_time` = now (UTC). Purge (FR-008): before each insert, delete finished jobs whose
`update_time` is older than 30 minutes, with the cutoff computed in Rust and passed as a UTC
literal without offset (B7: offsets and interval arithmetic do not work in the engine).

**D7 — `ADD CONSTRAINT … NOT VALID` through the core engine.** The server module
`constraints.rs` turns a planned `DdlAction::AddConstraintNotValid` into the core engine's `ALTER
TABLE t ALTER COLUMN c TO <c's full definition + REFERENCES …/CHECK (…)>` (`ast::AlterTableBody::
AlterColumn`), prepared with `PgConnection::inner().prepare_translated_stmt(stmt, original_sql)`
and run in the session's transaction. The column's current definition comes from the engine
schema. Single-column FKs (with ON DELETE/ON UPDATE actions) and CHECKs naming one column map to a
column constraint; multi-column FKs, table-level CHECKs over several columns and `DEFERRABLE` are
refused with `0A000` (µ text, FR-021a). The constraint name is kept. **This path is unproven**:
task T030 is a spike that must show, at the pinned rev, that (a) the statement prepares on a
PG-dialect connection, (b) new rows are checked (`23503`/`23514` with the constraint name), (c)
existing violating rows are not checked, (d) the table's data, indexes and other constraints
survive, (e) `pg_constraint` shows the constraint. If the spike fails, the fallback is a
minimal generic Turso patch to the PG translator mapping `AtAddConstraint` (FK/CHECK, `NOT
VALID`) onto the same core path — which would be the repository's first patch and requires
solving the `patch-crate` git-workspace constraint first (constitution II); this is then a
blocking question for the owner (plan "Seams"). Adds `turso_parser` (same pinned rev) as a server
dependency for the AST types.

**D8 — VALIDATE.** `ALTER TABLE ASYNC t VALIDATE CONSTRAINT c`: the server reads `c` from
`pg_constraint` (type, columns, referenced table/columns or check expression); a constraint that
is not on `t` gives `42704`. It runs a PostgreSQL-dialect check query in the session's
transaction (FK: child rows with non-null keys and no parent; CHECK: rows where the expression is
false) and records the job `completed` or `failed` (details: PostgreSQL's violation text). The
statement itself succeeds either way, as on DSQL. `convalidated` stays as the engine reports it
(known gap if it cannot express NOT VALID, FR-022). If the catalog lacks what is needed (spike
T030 checks `pg_constraint` columns and `pg_get_constraintdef`), the definition recorded at ADD
time is kept in the job-adjacent server state instead — decided in the spike.

**D12 — Seams with 007 (M4).** 006 does not change autocommit execution, transaction start,
