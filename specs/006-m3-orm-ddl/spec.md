# Feature Specification: M3 — DDL that ORMs and migrations emit

**Feature Branch**: `006-m3-orm-ddl`

**Created**: 2026-11-12

**Status**: Draft

**Input**: User description: "M3 — DDL that ORMs and migrations emit.
1. CREATE [UNIQUE] INDEX ASYNC: pre-parse rewrite that strips ASYNC (libpg_query can't parse it); build the index synchronously and return a job_id row. Emulate sys.jobs and sys.wait_for_job, plus sys.dsql_major_version. Try doing this from our server/policy layer first; a Turso patch is a last resort.
2. Sequence CACHE 65536: accept it and ignore it (Turso requires CACHE 1).
3. GENERATED BY DEFAULT|ALWAYS AS IDENTITY: desugar to a sequence plus a default.
4. ADD CONSTRAINT … NOT VALID and ALTER TABLE ASYNC … VALIDATE CONSTRAINT: accept them and validate synchronously.
5. Wire in Dreamescaper's golden probes (MIT) as a conformance runner, fetched at test time at a pinned upstream commit (not vendored), and track the pass rate with a local script and report (CI workflows were removed from the repo).
Also: the DSQL rules that M2 deferred until the ASYNC rewrite exists (synchronous CREATE INDEX refused, identity/sequence CACHE rules, ADD CONSTRAINT / ADD COLUMN with constraint, ALTER COLUMN TYPE) — see specs/005-m2-dsql-rules.
Exit: Drizzle's migrations run cleanly against micro-dsql (Drizzle is the M3 target ORM, docs/plan.md §6.1); golden-probe pass rate is at or above ~60%."

## Context

Schema migrations written for Aurora DSQL use DDL that micro-dsql cannot run today. Observed on the
current `main` (2026-11-12, full record in [research.md](research.md) §1):

- `CREATE [UNIQUE] INDEX ASYNC …` and `ALTER TABLE ASYNC … VALIDATE CONSTRAINT …` fail with
  `42601` syntax errors; `sys.jobs`, `sys.wait_for_job` and `sys.dsql_major_version` do not exist
  (`42P01`, `3F000`).
- Identity columns fail (`0A000 column constraint GENERATED ... AS IDENTITY is not supported`, or
  a misleading `0A000 WITH (storage parameters) …` text when the identity has options);
  `CREATE SEQUENCE … CACHE 65536` fails (`0A000 CACHE 65536 (Turso sequences do not cache values,
  so CACHE must be 1) is not supported`).
- `ALTER TABLE … ADD CONSTRAINT` of any kind, with or without `NOT VALID`, fails with `42601 ALTER
  TABLE ADD CONSTRAINT is not supported`: the engine has no ADD CONSTRAINT at all (the description
  assumed it only lacked `NOT VALID`).
- Rules DSQL applies are missing: plain `CREATE INDEX`, `CREATE SEQUENCE` without `CACHE`,
  `ALTER TABLE … ADD COLUMN … DEFAULT 7` and `… NOT NULL` are accepted; refusals of `ADD
  CONSTRAINT`, `VALIDATE CONSTRAINT` and `DROP COLUMN` of a key column carry `42601` instead of
  DSQL's `0A000`.

Two facts change the shape of the exit criteria:

- **Drizzle's stock migrator cannot run on DSQL itself.** It creates its journal table with `id
  SERIAL PRIMARY KEY` (DSQL: `42704 type "serial" does not exist`) and applies all pending
  migrations in one transaction (DSQL: `0A000 multiple ddl statements not supported in a
  transaction`). The SQL `drizzle-kit generate` writes also needs DSQL adaptations (`ASYNC` on
  indexes, `NOT VALID` plus `ALTER TABLE ASYNC … VALIDATE` for foreign keys, `bigint` identities).
  So "Drizzle's migrations run cleanly" is read as: a Drizzle project written for DSQL, with its
  generated migrations in DSQL form, applied the way DSQL requires (one DDL per transaction), runs
  without error, and the ORM's queries work afterwards; the stock migrator fails on micro-dsql at
  the same statement and with the same error as on DSQL.
- **The golden-probe pass rate is already above 60%.** Replaying Dreamescaper's 242 recorded probes
  (commit `38a33bf`) against today's micro-dsql gives 157/242 = 64.9% with the upstream comparison
  rules (messages are advisory). This feature keeps the overall rate at or above 60% and makes the
  M3 cases (index, sys.*, identity/sequence, ALTER TABLE groups) pass.

Live DSQL also differs from the MiniStack reference used by `tests/psql/probes`: on DSQL
`sys.wait_for_job` is a **procedure** (`CALL sys.wait_for_job('<id>')`; `SELECT
sys.wait_for_job(…)` fails with `42809`), and `sys.dsql_major_version()` exists (MiniStack lacks
it). micro-dsql follows live DSQL (005 decision D1: live record > Dreamescaper > research/01 >
MiniStack).

## Clarifications

### Session 2026-11-12

The owner could not be asked during this run; each answer is the recommended default, chosen for
consistency with the constitution and docs/plan.md.

- Q: What counts as "Drizzle's migrations run cleanly"? → A: A DSQL-shaped Drizzle project (schema
  using `bigint` identities with explicit CACHE, generated migrations adapted per AWS guidance) is
  applied one statement per transaction by a small DSQL-style migration runner built on Drizzle's
  migration files, then drizzle-orm queries run; the stock `migrate()` is also run and must fail
  with `42704 type "serial" does not exist`, as on DSQL (see Context).
- Q: `SELECT sys.wait_for_job(…)` (MiniStack) or `CALL sys.wait_for_job(…)` (live DSQL)? → A: Live
  DSQL: `CALL` returns one row, column `succeeded`, boolean; `SELECT` fails with `42809
  sys.wait_for_job(text) is a procedure`. The probes keep differing on these lines; the probe
  README records the deviation.
- Q: What does `sys.wait_for_job` answer for a well-formed id that is not in `sys.jobs`? → A:
  `22023` `job <id> not found` (micro-dsql text; no live record). Malformed ids fail with DSQL's
  `22P02 Unable to convert text to UUID`.
- Q: Is `CREATE INDEX … USING btree` refused? → A: No. `btree` is the default access method and
  Drizzle writes it on every index; other methods are refused with MiniStack's `0A000 USING not
  supported for CREATE INDEX`. No live record exists for either.
- Q: How faithful must `GENERATED ALWAYS` be? → A: It is accepted and behaves like `BY DEFAULT`
  (an explicit value is stored instead of being refused with `428C9`); recorded as a known gap.
- Q: What happens to a `NOT VALID` constraint form the engine cannot enforce (for example a
  multi-column or `DEFERRABLE` foreign key)? → A: It is refused with `0A000` and a micro-dsql
  text naming the form, and listed in docs/known-gaps.md; a constraint is never accepted without
  enforcement. Single-column foreign keys and CHECK constraints must be enforced (the Drizzle exit
  depends on them).
- Q: Are the DSQL adaptations of the Drizzle example's generated migrations made by hand or by a
  script? → A: By hand, once, in the committed migration files; the example's README lists each
  edit (ASYNC, `NOT VALID` + `VALIDATE`, no `USING btree` needed) so they can be repeated for a new
  migration.

## User Scenarios & Testing *(mandatory)*

### User Story 1 - Asynchronous index DDL works as on DSQL (Priority: P1)

A migration creates indexes the DSQL way: `CREATE [UNIQUE] INDEX ASYNC …`, keeps the returned
`job_id`, waits with `CALL sys.wait_for_job('<job_id>')` and may inspect `sys.jobs`. On
micro-dsql the index exists as soon as the statement returns, the statement answers with a
`job_id` row like DSQL's, and the job surfaces as completed.

**Why this priority**: Every DSQL schema with an index uses this form; today it is a syntax error,
so no DSQL migration with an index runs at all.

**Independent Test**: `CREATE INDEX ASYNC i ON t (v)` returns one row, column `job_id`, a 26-character
lower-case base-32 value; `CALL sys.wait_for_job('<that id>')` returns `succeeded = t`;
`SELECT status, job_type, object_name FROM sys.jobs WHERE job_id = '<id>'` returns `completed |
INDEX_BUILD | public.i`; queries can use the index.

**Acceptance Scenarios**:

1. **Given** a table, **When** `CREATE [UNIQUE] INDEX ASYNC [IF NOT EXISTS] [name] ON t (…)` runs
   (with or without a name, partial `WHERE`, expression keys, `INCLUDE`, `NULLS [NOT] DISTINCT`),
   **Then** it succeeds with command tag `CREATE INDEX` and one row, column `job_id` (text), value
   matching `^[a-z2-7]{26}$`, and the index exists when the statement returns.
2. **Given** that job id, **When** `CALL sys.wait_for_job('<id>')` runs, **Then** it returns one
   row, column `succeeded`, value `t`.
3. **Given** that job id, **When** `sys.jobs` is queried (any SELECT, filter, projection or
   join), **Then** it has the row `status = completed`, `job_type = INDEX_BUILD`, `object_name =
   <schema>.<index>`, `class_id = 1259`, with `start_time`/`update_time` set; `sys.jobs` has
   DSQL's nine columns in DSQL's order.
4. **Given** `CREATE UNIQUE INDEX ASYNC` on a column with duplicate values, **When** it runs,
   **Then** it still returns a `job_id`, the job is `failed` with a detail naming the duplicate,
   `CALL sys.wait_for_job` returns `f`, and no usable unique index is left behind.
5. **Given** `CREATE INDEX` without `ASYNC` (any table, empty or not), **When** it runs, **Then** it
   fails with `0A000` `unsupported mode. please use CREATE INDEX ASYNC.`
6. **Given** `CREATE INDEX ASYNC` inside an explicit transaction or inside a `BEGIN; …; COMMIT`
   query string, **When** it runs, **Then** it counts as the transaction's one DDL and returns the
   `job_id` row; a rolled-back transaction leaves neither the index nor the job.
7. **Given** `SELECT sys.wait_for_job('<id>')`, **When** it runs, **Then** it fails with `42809`
   `sys.wait_for_job(text) is a procedure`; **given** a malformed id, `CALL` fails with `22P02`
   `Unable to convert text to UUID`; **given** a subquery argument, `CALL` fails with `0A000`
   `cannot use subquery in CALL argument`.
8. **Given** `SELECT * FROM sys.dsql_major_version()` or `SELECT sys.dsql_major_version()`,
   **When** it runs, **Then** it returns one row, column `dsql_major_version`, value `1`.

### User Story 2 - Identity columns and cached sequences work as on DSQL (Priority: P1)

A schema declares `bigint GENERATED BY DEFAULT|ALWAYS AS IDENTITY (CACHE 65536)` (what DSQL
documentation and ORMs emit) or `CREATE SEQUENCE … CACHE 65536`. micro-dsql accepts them and
numbers rows like PostgreSQL; the forms DSQL refuses are refused with DSQL's errors.

**Why this priority**: Identity columns are the DSQL replacement for `serial`, which M2 refuses;
without them no DSQL schema with generated keys runs.

**Independent Test**: `CREATE TABLE a (id bigint GENERATED BY DEFAULT AS IDENTITY (CACHE 65536)
PRIMARY KEY, v text)`, then `INSERT INTO a (v) VALUES ('x'), ('y') RETURNING id` returns `1`, `2`.

**Acceptance Scenarios**:

1. **Given** a `bigint` identity column with `CACHE 1` or `CACHE` ≥ 65536 and any of PostgreSQL's
   sequence options (`sequence name`, `INCREMENT BY`, `MINVALUE`, `MAXVALUE`, `START WITH`), in
   `CREATE TABLE`, **When** rows are inserted without a value, **Then** they get consecutive values
   from `START WITH` by `INCREMENT BY`, as PostgreSQL would assign them in a single session.
2. **Given** an explicit value for a `BY DEFAULT` identity, **When** it is inserted, **Then** it is
   stored as given.
3. **Given** `CREATE SEQUENCE s CACHE 65536` (or any CACHE ≥ 65536, or `CACHE 1`), **When** it
   runs, **Then** it succeeds and `nextval('s')` returns `1`, `2`, ….
4. **Given** an identity column or `CREATE SEQUENCE` without `CACHE`, **When** it runs, **Then** it
   fails with `0A000` and DSQL's text (`identity column is not supported without an explicit cache
   size. please define CACHE greater than or equal to 65536 or equal to 1`, or the same with
   `CREATE SEQUENCE is not supported …`).
5. **Given** a `CACHE` between 2 and 65535 (identity or sequence, also in `ALTER SEQUENCE`),
   **When** it runs, **Then** it fails with `0A000` `CACHE must be 1 or at least 65536`.
6. **Given** an identity column of type `integer` or `smallint`, **When** it runs, **Then** it fails
   with `0A000` `datatype <type> not supported, identity column type must be bigint`.
7. **Given** a table with an identity column, **When** the table is dropped and created again
   with the same definition, **Then** the second CREATE succeeds and numbering restarts.

### User Story 3 - Constraints on existing tables follow DSQL's NOT VALID / VALIDATE flow (Priority: P1)

A migration adds a foreign key or CHECK to an existing table the only way DSQL allows: `ALTER
TABLE t ADD CONSTRAINT c FOREIGN KEY … NOT VALID` (or `CHECK (…) NOT VALID`), then `ALTER TABLE
ASYNC t VALIDATE CONSTRAINT c`, then waits on the returned job. ORMs (Drizzle) emit foreign keys
exactly this way, as separate statements after the CREATE TABLEs.

**Why this priority**: Every Drizzle schema with a relation emits `ALTER TABLE … ADD CONSTRAINT …
FOREIGN KEY`; the engine refuses all forms today.

**Independent Test**: after `ADD CONSTRAINT fk FOREIGN KEY (parent) REFERENCES p (id) NOT VALID`,
inserting a child row with a missing parent fails with `23503`; `ALTER TABLE ASYNC c VALIDATE
CONSTRAINT fk` returns a `job_id` whose job completes when all existing rows satisfy the
constraint and fails when one does not.

**Acceptance Scenarios**:

1. **Given** an existing table, **When** `ADD CONSTRAINT <name> FOREIGN KEY (…) REFERENCES …
   [ON DELETE/ON UPDATE <action>] NOT VALID` runs, **Then** it succeeds with tag `ALTER TABLE`,
   existing rows are not checked, and new or updated rows are checked (`23503` with PostgreSQL's
   message for a missing parent).
2. **Given** an existing table, **When** `ADD CONSTRAINT <name> CHECK (…) NOT VALID` runs, **Then**
   it succeeds, existing rows are not checked, and new or updated rows violating it fail with
   `23514`.
3. **Given** a NOT VALID constraint, **When** `ALTER TABLE ASYNC t VALIDATE CONSTRAINT <name>` runs,
   **Then** it returns tag `ALTER TABLE` and a `job_id` row; the job is `completed` and
   `CALL sys.wait_for_job` returns `t` when every existing row satisfies the constraint, otherwise
   the job is `failed` with a detail naming the violation and `wait_for_job` returns `f`.
4. **Given** `ADD CONSTRAINT` of a FOREIGN KEY or CHECK without `NOT VALID`, or of a PRIMARY KEY,
   UNIQUE or EXCLUDE constraint, **When** it runs, **Then** it fails with `0A000` `unsupported ALTER
   TABLE ADD CONSTRAINT statement`.
5. **Given** `ALTER TABLE t VALIDATE CONSTRAINT c` without `ASYNC`, **When** it runs, **Then** it
   fails with `0A000` `unsupported ALTER TABLE VALIDATE CONSTRAINT statement`.
6. **Given** a constraint name that does not exist on the table, **When** `ALTER TABLE ASYNC …
   VALIDATE CONSTRAINT` runs, **Then** it fails with `42704` `constraint "<name>" of relation
   "<table>" does not exist` (PostgreSQL's text).

### User Story 4 - A DSQL-shaped Drizzle project migrates and runs (Priority: P1)

A developer using Drizzle (docs/plan.md §6.1) points their test setup at micro-dsql, applies the
project's migrations the DSQL way, and runs the application's queries through drizzle-orm.

**Why this priority**: This is M3's exit criterion and the reason the DDL work exists.

**Independent Test**: one command starts from a fresh micro-dsql, applies the committed
Drizzle migrations of the example project (tables with identity keys, uuid/jsonb/numeric/
timestamptz columns, a foreign key, a unique index and a plain index), runs a CRUD and transaction
smoke through drizzle-orm, and exits `0`; the stock migrator is also run and its failure matches
DSQL's.

**Acceptance Scenarios**:

1. **Given** a fresh micro-dsql, **When** the example project's migrations are applied one statement
   per transaction, **Then** every statement succeeds, the migration journal records them, and a
   second run applies nothing.
2. **Given** the migrated schema, **When** the smoke runs insert-returning, select with join and
   filter, update, delete and an explicit transaction through drizzle-orm, **Then** results match
   the expected values.
3. **Given** a fresh micro-dsql, **When** Drizzle's stock `migrate()` runs, **Then** it fails with
   `42704 type "serial" does not exist` at its journal-table statement, as on DSQL.
4. **Given** the check, **When** the Rust gate (`cargo test --workspace`) runs, **Then** it does not
   need Node, npm or network access.

### User Story 5 - Conformance against live-DSQL recordings is measured (Priority: P2)

A maintainer runs one local script that fetches Dreamescaper's golden probes at the pinned commit,
replays them against a running micro-dsql, and writes a report with the overall and per-group pass
rate and every failing case, so progress toward DSQL is measured against live-cluster records.

**Why this priority**: The repository has no CI; a repeatable local measurement is the only way to
see regressions and progress across milestones.

**Independent Test**: with micro-dsql running, the script exits `0`, writes a dated report under
`reports/`, and the report states a pass rate (today 157/242).

**Acceptance Scenarios**:

1. **Given** a running micro-dsql, **When** the script runs, **Then** it fetches the probes at the
   pinned commit recorded in this repository (nothing of the suite is committed), replays them, and
   writes `reports/conformance-<date>.md` with total and per-group pass counts and the list of
   failing cases with golden and observed outcome.
2. **Given** a pass rate below the configured threshold (default 60%), **When** the script runs,
   **Then** it exits non-zero; above it, it exits `0`.
3. **Given** the script, **When** it runs twice against fresh servers, **Then** the pass counts are
   identical.
4. **Given** a missing prerequisite (toolchain, network, unreachable server), **When** the script
   runs, **Then** it stops with a message naming what is missing and exit status `2`.

### User Story 6 - ALTER TABLE forms DSQL refuses are refused (Priority: P2)

A migration uses an ALTER TABLE form DSQL does not support (ADD COLUMN with a default or
constraint, ALTER COLUMN TYPE, SET NOT NULL, dropping a primary-key column). micro-dsql refuses it
with DSQL's SQLSTATE and message, instead of running it or refusing it with an engine-specific
`42601`.

**Why this priority**: ORMs generate `ADD COLUMN … NOT NULL DEFAULT …` for schema changes; on DSQL
that fails, so it must fail locally.

**Independent Test**: `ALTER TABLE t ADD COLUMN d int DEFAULT 0` fails with `0A000` `ALTER TABLE
ADD COLUMN with constraint not supported` and the column does not exist.

**Acceptance Scenarios**:

1. **Given** `ADD COLUMN` with `DEFAULT`, `NOT NULL`, `CHECK`, `UNIQUE`, `PRIMARY KEY`, `REFERENCES`
   or identity, **When** it runs, **Then** it fails with `0A000` `ALTER TABLE ADD COLUMN with
   constraint not supported`; plain `ADD COLUMN [IF NOT EXISTS] c <type>` still succeeds.
2. **Given** `ALTER COLUMN … [SET DATA] TYPE …`, **When** it runs, **Then** it fails with `0A000`
   `unsupported ALTER TABLE ALTER COLUMN ... SET DATA TYPE statement`.
3. **Given** `ALTER COLUMN … SET NOT NULL`, **When** it runs, **Then** it fails with `0A000` `SET
   NOT NULL is not supported (only DROP NOT NULL)`.
4. **Given** `DROP COLUMN` of a primary-key column, **When** it runs, **Then** it fails with `0A000`
   `cannot drop primary key column <name>`.
5. **Given** a refused ALTER inside an explicit transaction, **When** the next statement runs,
   **Then** it gets `25P02` (the refusal aborts the transaction, as for the M2 rules).

### Edge Cases

- `CREATE INDEX ASYNC` where `ASYNC` appears in a comment, a quoted identifier (`"async"`), a string
  literal, or as the index name (`CREATE INDEX async ON t (c)`): only the keyword in the DSQL
  position is removed; everything else is unchanged.
- `CREATE INDEX ASYNC public.i ON t (c)` (schema-qualified index name) fails with `42601` `syntax
  error at or near "."`, as on DSQL; the stripped text must not make it valid.
- `CREATE INDEX ASYNC IF NOT EXISTS i …` where `i` exists: succeeds, returns a `job_id`, nothing is
  built.
- An index with more than 8 key columns: `54011` `more than 8 column keys in an index are not
  supported`. `CREATE INDEX CONCURRENTLY`: `0A000` `CONCURRENTLY not supported for CREATE INDEX`.
- `CREATE INDEX ASYNC` that fails in the engine for another reason (unknown table or column):
  the engine's error is returned and no job is recorded.
- Errors on rewritten statements report positions against the client's original text.
- `sys.jobs` is read-only for clients: INSERT/UPDATE/DELETE/DDL on `sys.*` fail with `42501`
  `permission denied for table jobs` (PostgreSQL's text); `CREATE SCHEMA sys` fails as the schema
  already exists.
- Concurrent sessions creating indexes get distinct job ids; every session sees every committed
  job in `sys.jobs`.
- A file-backed database (`--data`) reopened later still has `sys.jobs` and its rows; finished jobs
  older than 30 minutes are removed when a new job is recorded (DSQL's purge rule).
- Identity column in a multi-statement query string or an explicit transaction: still one DDL for
  the discipline rules, even though more than one engine statement may run.
- An identity table whose CREATE fails in the engine after its sequence was made: no sequence is
  left behind.
- Extended protocol: Parse/Describe of `CREATE INDEX ASYNC …` and `CALL sys.wait_for_job($1)`
  describe the `job_id` / `succeeded` columns; parameters work as in the simple protocol.
- `ADD CONSTRAINT … NOT VALID` with a multi-column foreign key, or with `DEFERRABLE`: accepted and
  enforced for new rows if the engine can express it; otherwise refused with `0A000` and a
  micro-dsql text naming the form, and recorded as a known gap (never accepted without
  enforcement).

## Requirements *(mandatory)*

### Functional Requirements

**Asynchronous DDL and jobs**

- **FR-001**: Before parsing, micro-dsql MUST remove the `ASYNC` keyword that directly follows
  `CREATE [UNIQUE] INDEX` and `ALTER TABLE`, and record that it did so, without changing any other
  byte of the statement's meaning; positions in errors refer to the original text.
- **FR-002**: `CREATE [UNIQUE] INDEX ASYNC` MUST build the index before the statement returns and
  answer with tag `CREATE INDEX` and one row, column `job_id` (text), a fresh 26-character id from
  the alphabet `a-z2-7`, unique across the server's lifetime.
- **FR-003**: `ALTER TABLE ASYNC t VALIDATE CONSTRAINT c` MUST validate `c` against all existing
  rows before returning, mark it valid on success, and answer with tag `ALTER TABLE` and a
  `job_id` row; a failed validation still returns a `job_id` and records a failed job.
- **FR-004**: Every job MUST appear in `sys.jobs` with DSQL's columns in DSQL's order (`job_id
  text, status text, details text, job_type text, class_id oid, object_id oid, object_name text,
  start_time timestamptz, update_time timestamptz`); `job_type` is `INDEX_BUILD` or
  `VALIDATE_CONSTRAINT`; `status` is `completed` or `failed`; `object_name` is
  `<schema>.<object>`. `sys.jobs` MUST be queryable with ordinary SQL from any session. A job
  recorded inside an explicit transaction is visible to other sessions only after COMMIT and is
  discarded on ROLLBACK.
- **FR-005**: `CALL sys.wait_for_job(<text>)` MUST return one row, column `succeeded` (boolean):
  `t` for a completed job, `f` for a failed one. A malformed id fails with `22P02` `Unable to
  convert text to UUID`; a well-formed unknown id with `22023` `job <id> not found`; a subquery
  argument with `0A000` `cannot use subquery in CALL argument`. Using it as a function (`SELECT
  sys.wait_for_job(…)`) fails with `42809` `sys.wait_for_job(text) is a procedure`.
- **FR-006**: `sys.dsql_major_version()` MUST return `1` (integer, column `dsql_major_version`),
  both as `SELECT sys.dsql_major_version()` and `SELECT * FROM sys.dsql_major_version()`.
- **FR-007**: Clients MUST NOT be able to modify `sys.jobs` or create objects in `sys`; such
  statements fail with `42501` and PostgreSQL's `permission denied …` text.
- **FR-008**: Finished jobs older than 30 minutes MUST be removed when a new job is recorded.

**Identity columns and sequences**

- **FR-010**: `bigint GENERATED {BY DEFAULT|ALWAYS} AS IDENTITY [( <sequence options> )]` in
  `CREATE TABLE` MUST be accepted when CACHE is 1 or ≥ 65536, and MUST assign values from an
  associated sequence (named by `sequence name` if given, else `<table>_<column>_seq`) honouring
  `START WITH`, `INCREMENT BY`, `MINVALUE` and `MAXVALUE`. The client's statement counts as one
  DDL statement.
- **FR-011**: Dropping a table MUST also drop the sequences created for its identity columns.
- **FR-012**: `CREATE SEQUENCE` and `ALTER SEQUENCE` with `CACHE` ≥ 65536 MUST be accepted; the
  cache value has no observable effect (numbering is as with `CACHE 1`).
- **FR-013**: DSQL's identity and sequence rules MUST be enforced, with these errors (all `0A000`):
  missing CACHE on an identity (`identity column is not supported without an explicit cache size.
  please define CACHE greater than or equal to 65536 or equal to 1`); missing CACHE on `CREATE
  SEQUENCE` (`CREATE SEQUENCE is not supported without an explicit cache size. please define CACHE
  greater than or equal to 65536 or equal to 1`); CACHE between 2 and 65535 (`CACHE must be 1 or at
  least 65536`); identity on a non-`bigint` column (`datatype <type> not supported, identity column
  type must be bigint`).

**Constraints on existing tables**

- **FR-020**: `ALTER TABLE … ADD CONSTRAINT <name> FOREIGN KEY (…) REFERENCES … [actions] NOT VALID`
  MUST be accepted and the foreign key enforced for rows written afterwards; existing rows are not
  checked.
- **FR-021**: `ALTER TABLE … ADD CONSTRAINT <name> CHECK (…) NOT VALID` MUST be accepted and the
  check enforced for rows written afterwards; existing rows are not checked.
- **FR-021a**: A `NOT VALID` foreign key or CHECK form the engine cannot enforce MUST be refused
  with `0A000` and a micro-dsql text naming the form (rule catalogue source µ), never accepted
  without enforcement.
- **FR-022**: A NOT VALID constraint SHOULD be reported as not validated in `pg_constraint`
  (`convalidated = f`) until a successful `VALIDATE`, then `t`; if the engine's catalog cannot
  express it, the difference is recorded in docs/known-gaps.md.
- **FR-023**: Every other `ADD CONSTRAINT` (FK or CHECK without `NOT VALID`, PRIMARY KEY, UNIQUE,
  EXCLUDE) MUST fail with `0A000` `unsupported ALTER TABLE ADD CONSTRAINT statement`;
  `VALIDATE CONSTRAINT` without `ASYNC` with `0A000` `unsupported ALTER TABLE VALIDATE CONSTRAINT
  statement`.

**Deferred DSQL DDL rules (from 005, D9)**

- **FR-030**: `CREATE INDEX` without `ASYNC` MUST fail with `0A000` `unsupported mode. please use
  CREATE INDEX ASYNC.`; `CONCURRENTLY` with `0A000` `CONCURRENTLY not supported for CREATE INDEX`;
  an access method other than `btree` with `0A000` `USING not supported for CREATE INDEX`; more
  than 8 key columns with `54011` `more than 8 column keys in an index are not supported`.
- **FR-031**: `ALTER TABLE … ADD COLUMN` with any column constraint or default (DEFAULT, NOT NULL,
  NULL-with-constraint, CHECK, UNIQUE, PRIMARY KEY, REFERENCES, GENERATED) MUST fail with `0A000`
  `ALTER TABLE ADD COLUMN with constraint not supported`.
- **FR-032**: `ALTER COLUMN … TYPE` MUST fail with `0A000` `unsupported ALTER TABLE ALTER COLUMN ...
  SET DATA TYPE statement`; `ALTER COLUMN … SET NOT NULL` with `0A000` `SET NOT NULL is not
  supported (only DROP NOT NULL)`; `DROP COLUMN` of a primary-key column with `0A000` `cannot drop
  primary key column <name>`.
- **FR-033**: The new rules MUST follow the M2 rule conventions: refusal before the engine runs,
  first matching rule wins, refusal inside a transaction aborts it, an aborted transaction answers
  `25P02` instead, one debug log line per refusal with the rule id, and one row per rule in the
  rule catalogue with its source.

**Drizzle exit check**

### Key Entities

- **Job**: one asynchronous DDL operation as DSQL reports it: id (26 base-32 characters), status,
  details, type, the object it concerns (class, object id, qualified name), start and update
  times. Shared by all sessions of the server; persisted with the database.
- **Rewrite record**: what was changed in a statement's text before it reached the engine (ASYNC
  removed, identity desugared, CACHE normalised, NOT VALID handled), kept with the statement's plan
  so the server knows to answer with a job row and errors keep original positions.
- **Identity sequence**: the sequence behind an identity column, owned by its table.
- **Conformance report**: date, pinned upstream commit, target, totals, per-group counts, failing
  cases.

## Assumptions

- Live DSQL behaviour wins over the MiniStack reference when they differ (005 D1); texts without a
  live record come from MiniStack, Dreamescaper's rule file or PostgreSQL, in that order, and are
  marked in the rule catalogue.
- `job_type` for validation is `VALIDATE_CONSTRAINT` (no live record; Dreamescaper's choice).
- Jobs are always complete (or failed) when their statement returns; `submitted`/`processing` are
  never observed. DSQL's "index INVALID after a failed build" becomes "no index" (known gap).
- `GENERATED ALWAYS` identities accept explicit values (known gap); `OVERRIDING SYSTEM VALUE` is
  accepted and has no effect.
- `ALTER TABLE … ALTER COLUMN … ADD GENERATED AS IDENTITY`, `SET GENERATED`, `RESTART`, `DROP
  IDENTITY`, `ADD UNIQUE USING INDEX`, `SET STORAGE`, `ALTER COLUMN SET/DROP DEFAULT` and `DROP NOT
  NULL` (DSQL supports them; the engine refuses most) are out of scope for this feature and stay as
  the engine answers them; they are listed in docs/known-gaps.md.
- The Drizzle example uses the drizzle-orm, drizzle-kit and node-postgres versions current on
  2026-11-12 (0.45.4, 0.31.11, 8.23.1), pinned by a lockfile; Node 22 or newer is a prerequisite of
  that check only.
- The conformance runner uses the upstream recorder and comparison code at the pinned commit
  (`38a33bf283d7670b30dc959e8f38d0cf4eef1ddc`, the commit 005 used for message texts); a Go
  toolchain is a prerequisite of that script only.
- Feature 007 (M4) owns autocommit execution, transaction start and snapshot behaviour, the
  doomed-transaction flag, `FOR UPDATE` and the `55P03` mapping; this feature does not change them.
